BeaverBuddiesStability Fork

Build one Timberborn colony together, in real time.

A fork of thomaswp's BeaverBuddies: everyone plays the same colony, each with their own camera, plus Steam friend invites, a connection panel with chat, your friends' cursors, and a long list of crash and desync fixes.

Download 1.1.15 Install guide

Replaces the Workshop BeaverBuddies. The two change the same parts of the game and can't be installed together: unsubscribe from the Workshop version first. Every player needs this fork, the same download.

1.1.15 has been played and works. It is a bug-fix release on top of 1.1.13, the last release with new features, and 464 automated checks pass.

This fork is feature-complete: it gets fixes and updates for new Timberborn versions. New features go into Timber Together, which can also give each player a colony of their own.

Playing together takes three steps

No router settings, no virtual networks. If you both have Timberborn on Steam, you are a few clicks away.

  1. Everyone installs the mod

    Every player installs the same version of the mod (the same download) and runs the same game version, then restarts the game. Install guide

  2. The host invites a friend

    Load a save, choose Host co-op game, then Invite Friends and pick your friend in Steam's overlay.

  3. Your friend joins, you start

    When your friend appears in the player list, the host chooses Start Game. Everyone builds in the same colony.

What you get

Everything the original BeaverBuddies does, plus the parts that make a long co-op session actually work.

  • Steam friend invites

    Invite a friend from Steam's own overlay. Connections go straight between you when Steam finds a route and are relayed through Steam otherwise, so there is no Hamachi and no port forwarding. Direct IP still works too.

  • A connection panel

    See who is connected, each player's ping, whether you are in sync, and the tick rate at a glance, and chat with everyone in the game. A speed boost at the top of the chat adds to the game's speed for everyone. Collapse it to one line or hide it completely.

  • See your teammates

    Colored, translucent cursors with names, selection outlines, and Viewing / Editing labels on buildings. Restyle each player's cursor in the Player cursors dialog.

  • Fewer crashes and desyncs

    Fixes for the water, animation, random-number, saving, demolition and input problems that knocked sessions out of sync or crashed them. Each one, and how sure we are.

  • Problems are explained

    Joining with a different build is refused before the save is sent, and a warning lists any mods that differ. Failed connections and multiplayer actions end with a plain-language reason instead of a silent hang.

  • Quicker and lighter

    A guest's actions reach the host sooner (roughly 0.3 seconds at normal speed), the mod's work every tick and every frame has been trimmed, and over Steam the ping no longer climbs as the game speeds up.

Skip the port forwarding

Choose Invite Friends and your friend gets a normal Steam invitation. If their game is closed, Steam launches it and joins for them.

Confirmed  Working in real playtests between the maintainer and a friend.

  • Friends only. The host opens a friends-only lobby and only accepts players who joined it. A stranger who knows your Steam ID cannot connect.
  • Your address stays private. Valve documents that relayed connections keep players' IP addresses hidden from each other.
  • Direct IP still works. Both options are offered when you host, so Hamachi and port forwarding keep working. A problem with Steam doesn't stop you hosting over direct IP.
  • Clear errors. If a connection fails, you get Steam's own reason in plain language and in the log.
  • The current API. The original used Valve's older networking API, which Valve marks as deprecated. This fork uses the one Valve recommends.

Both players need to be online in Steam and to own Timberborn on Steam.

Know how your session is doing

A small panel in a corner of your screen during multiplayer games. It only reads: it sends no gameplay events, and if it ever fails it switches itself off.

StatusWhat it means
In syncNormal. Everything is running together.
Catching upGuests only: your game is a few ticks behind the host.
Waiting for hostGuests only: nothing has arrived from the host for a moment.
Connection unstableSomeone has stopped responding for five seconds.
Out of syncA desync was detected.
DisconnectedThe session has ended.
  • Each player is a name and a ping, host first. Your own row is bold, with a dash where the ping would be.
  • Ping is the round trip between you and that player. It is normal text at 80 ms or less, yellow up to 160 ms, and red for anything higher or no response.
  • The dot beside the status is green when you are in sync, yellow while catching up or waiting for the host, and red when the connection is unstable, out of sync or disconnected.
  • Tick rate and speed show how fast the simulation is really running, and guests see how many ticks they are behind the host (0 or 1 is normal).
  • Connection shows whether players are connected directly or through Steam.
  • The host also sees how far behind the slowest guest is and the lowest guest frame rate, and can click Ease off below to slow the game a little while a guest stays under a frame rate (Off, 20, 30, 45 or 60 fps).
  • A chat box sits below the panel. Everyone sees messages in the same order, and a player who joins later gets the whole conversation. Each name is drawn in the sender's cursor color, and the message stays in the normal text color.
  • Click the title to collapse it to a single line. Your choice is remembered.
  • Hide it or move it to any corner in Mod Settings, or bind the optional Toggle connection panel key.

Ping is measured by the mod's network layer, so it means the same thing over Steam, Hamachi and direct IP. Over Steam it includes a short wait for each game to serve Steam, which the mod keeps to a few milliseconds even at a high game speed.

See what your teammates are doing

Other players' cursors, selections and building edits show up on your screen, so you stop building on top of each other.

  • Cursors are colored and translucent, with a name label. Each player starts with a color of their own (the host orange, then blue, green, pink, purple, teal, red and lime for the guests), and you can change any of them. They are shared in world space, so cameras can be anywhere.
  • Selection outlines use the game's own outline in that player's color.
  • Viewing / Editing labels appear on buildings. It is an advisory notice, not a lock: both players can still change a building.

Make each cursor your own

Open Options (Esc) and choose Player cursors. Each connected player gets a card:

ControlRangeDefault
ColorTheir color, 10 presets, or exact RGBTheir color
Size50% to 300%100%
Transparency0% to 90%50%

These are display-only choices that stay on your machine. They are never sent to other players, are remembered by player name, and cannot affect the simulation.

The first card, You, in the chat, sets the color you see your own name in, in the chat. Only you see it: others still see your Ping Color, or the color for your player number.

Stability work, and how sure we are of it

Confirmed means it was checked in a real multiplayer game. Tested means automated checks cover it, but the exact situation it fixes hasn't been set up on purpose in a real game.

Confirmed in play Confirmed · 4

  • Water no longer depends on frame rate

    Players at different frame rates used to see different water, which caused desyncs. The water now follows the simulation's own clock. It resolved a reported "badtide" desync.

  • Animation crash fixed

    A path cursor that could move backward between ticks, and non-finite visual coordinates, no longer crash the game.

  • The ping stays low at a high game speed

    Over Steam, data used to wait for the end of every frame, and at a high game speed a frame is mostly simulation, so the ping grew with the speed. Steam is now also served between the ticks of a frame. At a true speed 7 the ping stayed under 100 ms, where it had been 200 to 300 ms.

  • Controls work after a disconnect

    Input state is recovered after a desync, a failed action or a lost connection, so the menu and controls keep working.

Covered by checks Tested · 12

  • Builds are checked before the save is sent

    The fork compares the game version and the exact mod build first, with a time limit and a clear message, instead of warning after the save has loaded.

  • A failed action stops safely

    If a multiplayer action fails, replay stops, the session pauses and peers are told, instead of two games quietly drifting apart.

  • More deterministic random numbers, saving and ordering

    Nested random-number scopes are restored even after errors, a stale saving flag is cleared, and water sources are applied in a consistent order.

  • Demolition fixes

    A replayed demolition selection that included already-demolished buildings no longer ends the session, and equal-distance demolition jobs are chosen deterministically.

  • The host can ease off for a slow guest

    The host picks a frame rate floor; while a guest stays below it, the host slows the game a little and speeds back up by itself. It never changes what happens in a tick.

  • More ways out of sync closed

    Planting marks the same tiles when players have sliced the view to different layers. A building is no longer refused on one computer while its player hovers a path that would join two districts. The Tick once key and dev mode's Ctrl keys no longer change one computer only. Nobody can join after something was placed or changed while the game waited to start, and joining closes before the first tick goes out, so a late joiner can't miss it.

  • A fuller desync check

    Guests compare all of the host's random-number state, so a desync is caught sooner. Every tick they also compare the entities that tick and where every walking character stands, and log the first difference, so a report says when the games first went apart.

  • A safer network reader

    A received message can only create multiplayer actions and their values, other mods' actions included. A guest that gets an action it can't read, for example from a mod only the host has, leaves with a message naming it instead of drifting apart, and the others play on.

  • Wonders on the tick

    The Earth Repopulator's plane launch and every Wonder's animation advance once per tick in co-op, the same for everyone. If a game update changes the code this relies on, the Wonders fall back to frame time and every other fix stays in place.

  • One lost link, not a frozen game

    A direct (IP) player whose connection dies no longer freezes the host and everyone else; they're dropped after 30 seconds, as over Steam. Something deleted in a tick is gone at once for everyone, and a building from a mod only one player has no longer stops the game.

  • Pump, valve and dev generator controls are shared

    A pump's flow rate, a throttling valve's limit on/off and the dev power generator's strength and flip used to change only the clicking player's game. Now every player gets the change on the same tick.

  • Unlocks, logging and long sessions

    Two players unlocking the same building at once pay once, and an unlock the science no longer covers is skipped instead of stopping the game. Turning on detailed logging mid-game no longer reads as a desync, a guest joining after Save and Rehost starts at the new session's speed boost, and a long session no longer keeps every menu and game it loaded in memory.

Every change, with its status, is in the changelog.

How it works, in one minute

Timberborn is a single-player game, so BeaverBuddies keeps every player's copy of the game identical instead of streaming one game to everyone.

  1. Everyone starts from the same save. The host sends the save when a friend joins.
  2. Every action is mirrored. Building, changing a recipe or setting a priority is sent to the host, which decides which tick it happens on and sends it to everyone.
  3. The game is deterministic. Given the same save and the same actions on the same ticks, every copy of the game plays out exactly the same.

That is why every player must run the same build, why other mods should match, and why nobody can join once the host has started. When something breaks that sameness, that is a desync. The original project's wiki explains the design in more detail.

Good to know before you play

  • Every player installs the same version of the mod (the same download) and runs the same game version. The mod refuses a different build when someone joins.
  • Other mods should match. When someone joins, both players get a warning listing any mods that differ. A guest missing a mod whose actions the host sends (MixedStorage, for example) leaves the game at the first such action, with the mod named, and the others play on. Settings are not compared, so keep simulation-affecting settings identical.
  • Join before the host starts. Nobody can join after Start Game, or once something has been placed, marked or changed while the game waited.
  • Desyncs can still happen. This fork removes known causes; it cannot promise none. Keep backups of your saves.
  • Tested with two players on Windows and Steam. Larger groups and other platforms have not been tried.
  • One BeaverBuddies at a time. Remove the Workshop BeaverBuddies (and don't enable Timber Together alongside this fork).

More answers are in the FAQ, and Troubleshooting covers what to do when something goes wrong.
